# USB Display 上位机｜项目规范

版本：v0.5 WPF UI 展示层设计基线　日期：2026-10-07

## 1. 适用范围

本规范约束后续 C# 原生桌面实现、协议适配、测试和交付。技术方案见 [软件技术架构](03_软件技术架构.md)，功能标准见 [PRD](02_PRD.md)，视觉及交互见 [UI 设计规范](06_UI设计规范.md)，任务关系见 [项目管理](04_项目管理.md)。

管理 UI 使用 WPF/XAML＋WPF UI，本地构建和测试可独立执行。依赖应符合技术架构中确定的模块职责和选型。

“必须”表示正确性或交付约束；建议参数可在有实测证据的评审中调整。原始附件保持原样，发现错误在交付文档登记，不直接改写来源以消除矛盾。

## 2. 工程与依赖

按架构文档划分 Desktop、Core、Windows、Rendering；不增加没有实际责任的公共层、插件总线或通用框架。

SDK、NuGet 包和原生依赖锁定版本；建项时记录实际补丁。启用 nullable 和 .NET 分析器；协议、原生内存和异步清理警告必须解决。新增依赖必须说明用途、许可、分发文件和替换理由。

建项时提供 global.json、集中包版本及 packages.lock.json，构建使用锁定还原。WPF-UI 和 CommunityToolkit.Mvvm 仅用于 Desktop；日志抽象可被 Core 使用，Serilog 实现限于适配／组合根。通过项目引用检查守住 Core 不依赖 WPF／Windows、Windows／Rendering 不引用 WPF-UI、ViewModel 不直接接收原生实现的边界。

T-07 锁定 WPF-UI 的具体稳定版本，验证 .NET 10、目标 Windows build 与自包含发布兼容性；不使用浮动版本。保留其 MIT 许可及随包分发素材所需声明，额外字体／图标单独核查分发许可。升级 WPF-UI 时检查 API 与资源键变化，并回归 TC-29、TC-30、TC-33，涉及更新界面时补验 TC-34～TC-38。

首版 Windows x64 自包含发布；不默认启用 AOT、裁剪或单文件压缩。原生依赖必须列入发布清单，不能依靠开发机 PATH 才运行。

## 3. C# 与界面代码

- 类型／公开成员使用 PascalCase，局部变量使用 camelCase，异步方法以 Async 结尾。
- UI 使用绑定和命令；ViewModel 不直接调用 WinUSB、访问设备句柄或解析二进制。
- ViewModel 采用 CommunityToolkit.Mvvm；不再维护重复的 ObservableObject 或异步 ICommand 框架。命令状态不能替代 Core 的操作互斥与能力检查。
- code-behind 只处理窗口、Dispatcher 和视图特有行为。
- Core 不引用 WPF 类型；原生签名及 SafeHandle 放在 Windows 工程。
- 对协议数值写明单位、字节序和来源，不散落魔法常量。
- 只为确定责任创建接口，不为每个类生成一层空接口。
- 不吞掉异常后报告成功；预期取消与实际故障分开处理。

界面先加载 WPF UI 的主题和控件资源，再加载项目语义资源与必要覆盖，统一颜色、字体、间距和状态样式。优先复用控件及其交互模板；业务组件只组合所需展示，不复制整套库模板。导航、对话框与短时提示通过 Desktop 内的服务适配，设备与更新状态始终来自各自用例快照。不得引入未实现入口、示例业务数据或大段解释性占位文案。必要技术详情集中到诊断页。

控件模板保留焦点、键盘与自动化语义；颜色随高对比度更新，布局响应客户区大小。UI Preview 来源必须标明草稿、活动或历史；状态改变与异步完成只通过快照投影，不能双向绑定设备实际状态。

## 4. 异步与生命周期

UI 不调用 .Wait() 或 .Result 等待 I/O。除事件处理器外不使用 async void；事件处理器必须捕获并报告异常。

设备状态只有一个写入者。原生回调提交事件，不能直接修改 ViewModel。异步结果携带会话代次和操作号，旧代次结果丢弃并记录。

主题帧还须携带内容修订号；同一会话中的迟到渲染结果不得覆盖新主题。指标、渲染请求及 UI 预览均有上限，不能只限制 USB 待发槽却放任 Dispatcher 积压。窗口隐藏停止预览通知，不停止已应用主题。

USB/HID 使用有界超时、取消与完成收敛。CancellationToken 已取消不代表内核 I/O 已停止；释放缓冲和句柄前确认完成。不得使用 Thread.Abort 或通过丢弃后台任务代替清理。

WPF 绘图对象在专用 STA Dispatcher 创建和使用。跨线程只传不可变数据、独立字节缓冲或已成功 Freeze 的图像。JpegBitmapEncoder 等有线程归属的对象不跨线程共享。

一帧只允许一个所有者：渲染完成交给待发槽，发送器取走后负责释放；替换的旧待发帧由槽释放。已经开始发送的帧不能中途替换。

使用单调时钟测超时与耗时，纯逻辑测试注入 TimeProvider 控制时间。同一用户会话二次启动不得再枚举接管设备；关闭至托盘与显式退出由统一 ApplicationLifetime 管理，页面生命周期不拥有设备会话。

## 5. 协议硬规则

1. 端点地址、最大包长和报告长度从当前设备取得，不硬编码猜值。
2. 描述符长度、尺寸和能力必须检查；目标分辨率冲突时禁止推流。
3. 0x68 为 8 字节头，0x69 为 11 字节头；偏移和长度为 24 位大端。
4. 分片总长度≤T；尾片必须存在且唯一；重组得到的 JPEG 与输入完全一致。
5. JPEG 必须完整且能解码，不能只检查 SOI；检查尺寸、格式及实际设备兼容性。
6. 空帧和超过已验证最大帧的输入不发送；降质次数有上限。
7. 命令和分片共用单写者调度，命令不插在一帧分片之间。
8. 超时、短写、取消后不直接续传剩余字节，不盲目重发当前片。
9. parser reset 的语义必须经固件确认；管道 reset 不等同拼帧状态 reset。
10. 不发 BLANK_MODE=0x02 作为正常退出或纯熄屏。
11. 未冻结、未知版本或能力不支持的扩展命令不发送。
12. ZLP 按已验证设备配置处理，不向 JPEG 或协议包填充未定义内容。
13. Source 文档中的“绝不冲突”和“静默忽略”不作为未知命令安全依据。

控制应答区分“已发送”“已受理”“已执行”“结果未知”。模式切换以同一设备的目标态可操作为完成，不以发送成功或目标 PID 单独出现为完成。

## 6. 配置与输入

保存已应用配置与编辑草稿；主题应用失败时保留用户输入并显示状态，不把失败草稿写为设备实际配置。

草稿、ActiveProfile、DeviceProfile 与呈现证据分别处理。候选首帧完成后才能提交恢复配置；传输成功但保存失败，当前会话可用候选配置，恢复配置保持旧值，提供只保存本地的重试。任何阶段结果未知都不能报“设备已显示”。应用操作不清除后续编辑产生的新草稿。

配置通过临时文件写入后替换，包含 schemaVersion；损坏时保留副本并恢复可用配置或默认值。设备配置键不能只使用 VID/PID。升级遇到未知高版本 schema 不静默覆盖。

本地图片限制按架构文档执行；读取尺寸后再分配，处理损坏图片、方向元数据和透明背景。素材复制后再作为已应用引用。首版不执行主题中的代码，不加载外部任意 XAML，不实现压缩主题包导入。

## 7. 日志与错误

用户提示使用“原因＋可执行动作＋错误编号”。日志记录底层错误、调用阶段、会话和操作关联。不要在界面堆栈输出或仅显示“发生错误”。

默认单文件 10MiB、最多 5 个，本地滚动。正常逐帧信息聚合为周期统计；临时调试也必须有大小限制。诊断包包含版本、兼容信息、摘要配置和日志，不包含用户图片、完整个人路径、原始内存或凭据。

日志异步缓冲有界；队列丢弃和磁盘失败必须进入可见诊断状态。文件轮转使用库实现，但仍需验证包含在写文件在内的实际配额；正常关闭刷新，不能把尚在缓冲中的事件视为已落盘。

PC 指标和设备指标必须标注来源。超过 3 秒没有新值按 PRD 标过期。无反馈的 deviceDecoded/devicePresented 为空，不通过 usbCompleted 估算后冒充。

## 8. 测试分层

| 层次 | 覆盖 | 能证明什么 |
|---|---|---|
| 纯逻辑 | 编码、分片、状态决策、配置验证、命令关联 | 算法和业务规则正确 |
| 展示与渲染 | ViewModel、命令、快照投影、STA 渲染与帧修订 | UI 状态映射、预览隔离和输出尺寸正确 |
| Windows 适配 | 句柄／取消、通知、原生调用返回、文件与线程归属 | 应用对系统行为的处理正确 |
| 模拟设备 | 短写、迟到事件、坏报告、ACK 丢失 | 主机异常路径可控 |
| 真实设备 | 解码、显示、重枚举、驱动、熄屏、长稳 | 冻结环境内的端到端行为 |
| 原生界面验收 | 实际 WPF 窗口、各状态截图、DPI、键盘、读屏器 | 真实布局、可读性与桌面交互正确 |

测试必须验证外部可观察结果，不能只断言内部方法被调用。桌面截图不能替代设备屏幕照片；模拟器通过不能关闭实机验收任务。

| TC-37 | 安装前有未保存草稿／配置、模式切换、部分帧写或清理失败；正常主题态／副屏态／熄屏／无设备更新 | 保存与清理成功后才交接；失败留在原进程；安装重启不主动切模式或复位；hooks 不打开设备、不争用普通单实例锁 |
| TC-38 | 从真实安装的旧版升级到新版；安装文件占用、更新器启动失败、配置迁移失败、新版启动失败及完整包修复 | 当前版本核实后才报成功；配置／素材／草稿保留；备份可用；失败可定位并按说明修复；不虚报自动回滚 |

对于 TC-05：分片器可使用任意字节序列验证长度算术；完整发送入口另用真实 JPEG 检查有效性，不要求 1 字节样本被当成合法 JPEG 发送。枚举分片长度不能代替 USB 边界实测。

V0 必测 TC-01～TC-19、TC-26～TC-33 中已实现主题范围；TC-27 的 24h 长稳为 V1 必过，V0 至少完成 1h 稳定性实验并明确差异。V1 全部适用场景必须通过；能力限制须与 PRD 一致，不能用“不适用”掩盖双模／纯熄屏未完成。

TC-29／TC-30 使用实际 WPF 窗口；硬件未就绪时可以用明确标注的模拟状态检查布局，但模式、电源和呈现语义仍需 TC-20～TC-23 实机证据。截图记录客户区 DIP、屏幕像素、DPI 和文字缩放，不以缩放图片冒充不同窗口验收。

TC-34～TC-38 为 V1 必测；至少准备两个不同版本、相同 packId 的真实签名安装包及隔离测试发布源，记录更新前后版本、包哈希、配置备份、更新器日志和实际安装结果。测试索引不能写入正式发布源；断网测试须同时操作核心功能。

## 10. 证据记录

每次实机测试记录：TC 编号、日期、执行人、应用版本／提交、固件版本、驱动版本、Windows build、PC、USB 控制器与端口／Hub／线材、设备身份、输入素材、步骤、预期、实际和结论。

性能数据注明采样间隔与统计口径；P95 保留原始样本，失败样本不得从成功率中删除。设备计数无法读取时明确使用的外部观测方法，不编造“零丢帧”。

## 11. 代码评审与版本管理

任务开发分支默认 feature/简短名称；按仓库实际主分支提交评审，不假设分支保护和远程平台已经配置。不要修改无关工作或把原始附件顺手格式化。

提交描述说明问题和行为变化。评审包含：需求／任务编号、改动范围、验证证据、仍未覆盖的实机情况。协议改变必须同时更新字段说明和匹配固件版本。

重点检查：旧会话事件、部分写结果、原生缓冲释放、状态虚报、模式切换期间写入、配置与设备实际值混淆。单纯增加重试、捕获全部异常或扩大队列不构成正确修复。

## 12. 构建与发布规范

实现后提供可在普通 Windows 开发机执行的构建入口：锁定依赖还原、Release 构建、离线测试、win-x64 发布、打包。命令及所需 SDK 版本写入仓库；自动执行环境调用同一入口，不复制另一套构建规则。

普通构建不执行驱动安装、模式切换、固件升级或硬件压力测试。硬件验收显式选择环境和设备。

正式发布检查：与测试一致的构建产物、应用与驱动签名、依赖许可、自包含运行文件、版本／哈希、安装和卸载说明、固件兼容表。软件更新工具版本由 T-31 锁定，T-25 验证安装产物，本文不指定外部 CI 服务。

软件更新使用 T-31 锁定的 Velopack SDK／打包工具和稳定发布身份，T-25 应用该基线。先完成产物签名与校验，再上传版本包，最后发布版本索引；同版本包不覆盖重写。应用更新不得携带自动执行的驱动安装或固件升级动作。客户端发布地址固定，不能在配置中接受任意下载地址和执行命令。

Velopack hooks 在普通应用初始化之前处理；关闭启动自动应用更新。主程序只在 UpdateRestart 清理流程完成后交接，不能先退出再尝试保存配置。配置、素材和日志置于安装根目录之外，迁移具备备份和可诊断失败路径；软件回退与配置恢复分别验证。

## 13. 文档与协议一致性

需求编号、功能编号、任务编号和测试编号必须可追踪。修改协议上限、默认值或发布范围时同时修改相关文档，不能留下两个“当前基线”。

协议草案须经主机与固件双方确认并验证后才能作为实现契约。测试报告分别记录模拟测试和实机测试的结果；缺少协议或硬件条件时，记录阻塞及其影响范围。
