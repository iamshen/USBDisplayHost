# USB Display 上位机｜项目规范

版本：v0.1 评审稿　日期：2026-10-06

## 1. 适用范围与约束级别

本规范适用于本项目 C# 上位机、协议接口、与固件的联调、测试、CI和发布。它是建议纳入仓库的工程基线，未声称用户已批准所有新增规则。

“必须”是合并或发布门槛；“应”是默认做法，偏离需有理由；“可”是经过评估的选项。两份附件是原始依据，不直接作为无条件正确的实现规范；冲突处理以《01_需求分析》ISS清单与已批准的协议契约为准。

首要原则：**状态真实、协议明确、资源有主、失败有界、证据可追溯。**

## 2. 仓库与文档规范

仓库应包含 README、五份项目文档、docs/adr、docs/protocol、测试说明、构建说明、第三方许可与发布说明模板。源码/测试/工具/资源分开，完整目录见《03_软件技术架构》。

文档编号统一：REQ-xx为需求，FR-xx为PRD功能，AC-xx.x为验收条件，TC-xx为测试场景，ISS-xx为原文问题，ADR-xxx为技术决策，Txxx为文档任务码。Azure DevOps真实工作项ID另列，不混用Txxx。

协议文档必须包含：适用固件/硬件、协议版本、方向、完整字段布局、字节序、长度、单位、有效范围、能力条件、错误、超时、幂等性、兼容规则和golden vectors。命令号常量由同一份注册表生成或对照，禁止在多个模块复制不同版本。

涉及源文改动时保留“源文说法—发现的问题—评审结论—验证证据”，不能直接覆写原始附件后丢失依据。

## 3. 技术栈边界

### 3.1 允许的首版基线

.NET10、WPF、Blazor Hybrid、Fluent UI、Stateless、本地Windows传输、Skia/JPEG、JSON、Serilog、本地指标与Azure DevOps。具体SDK、NuGet和native DLL版本必须在最小验证后锁定。

### 3.2 不得未经ADR引入

Dapr sidecar、Orleans集群、Event Store、Kafka、Redis、PostgreSQL、EF Core、Kestrel中转、远程登录服务、第二套UI组件库、脚本主题、自动OTA、跨平台宿主和多设备并发。不能以“用户平时使用这些技术”为理由增加本机USB链路的部署复杂度。

### 3.3 工具链一致

global.json锁定已验证SDK，Directory.Packages.props集中版本，锁文件进入仓库。开发机与CI同一feature band。禁止浮动依赖、构建时拉取未知最新native二进制、用未记录的本机DLL解决CI失败。

net10.0的IDE要求按微软SDK/VS支持矩阵执行，不因个别教程标题仍提到VS2022就降低要求。[W1] Fluent Hybrid初始化按当前锁定版本验证，不能照搬旧版本脚本补丁；官方说明旧的.NET8及以下workaround不适用于.NET9及之后。[W2]

## 4. C# 编码规范

启用Nullable和适当的分析器；协议与Interop相关告警不得随意压制。提交代码不得包含生产路径中的`NotImplementedException`、测试假状态、空异常捕获或隐藏错误的默认返回值。

公共命名使用PascalCase，异步方法以Async结束，CancellationToken作为末参数；时长使用TimeSpan，不用无单位int；配置数值单位进入属性名或类型，如MaxJpegBytes、SwitchTimeout、BrightnessPercent。

运行时快照、能力和身份优先不可变。区分Desired、Reported、Confirmed，不能用一个Brightness或Mode字段同时表达用户期望和设备事实。传感器数值允许null并携带Quality，不用0代表不可用。

纯协议模块不依赖UI、文件、网络、线程睡眠或静态全局设备。Application只依赖端口接口，UI不接触SafeHandle或Byte[]协议结构。源代码中的魔法数仅在已命名协议常量或受审计的字段表中出现。

大小、偏移、索引转换使用明确范围检查；乘法/加法涉及外部长度时使用checked或等效防溢出。时间期限用单调时钟/TimeProvider，日志时间用UTC并在UI本地化；不能用可被调整的系统墙钟计算USB超时。

## 5. 异步、线程与资源规范

### 5.1 状态机单写者

Stateless实例不能被UI、HID和PnP线程同时触发；异步支持不代表线程安全。[W3] 所有模式和会话状态变更进入协调器。PnP回调不等待USB操作，不阻塞窗口线程；先通知再枚举并去重。[W4]

状态处理器不得等待必须由同一队列消费才能满足的事件。长操作作为可跟踪副作用启动，完成后投递带OperationId/Epoch的事件。异常和取消都必须回到明确终态。

### 5.2 三类队列不同处理

| 队列 | 默认规则 | 禁止事项 |
|---|---|---|
| 完整待发帧 | 容量1～2；新帧可替换旧帧 | 无界积压；把正在发送的半帧换掉 |
| 用户控制命令 | 有界；背压或返回Busy | 静默丢弃；无限排队 |
| 生命周期事件 | 优先处理、去重并保留对账信号 | 队列满后丢掉设备移除；使用旧句柄 |

有界Channel的丢弃路径必须归还帧资源。可使用itemDropped回调，但回调本身也要无异常且足够轻量。[W5]

### 5.3 所有权约定

创建者在转移前拥有资源；入队成功后由队列/消费者拥有；发送完成或丢弃后必须Dispose；入队失败仍由创建者释放。每条路径只能释放一次。

原生I/O未完成时，buffer不得归还ArrayPool/MemoryPool、解除pin或被复用。CancellationToken取消不是native完成的证据。SafeHandle、OVERLAPPED、事件句柄、Skia对象和编码器实例都必须有确定的关闭责任与次序。

禁止`.Result`、`.Wait()`堵塞UI；禁止为每一帧无限创建Task；禁止async void，除确需的UI事件适配外，即便UI事件适配也必须捕获并转交异常。所有周期任务受应用和会话生命周期的CancellationToken控制。

## 6. USB 与协议硬规则

以下规则必须进入代码评审检查表：

1. display接口号、alternate setting和Bulk OUT端点从描述符发现，不把0x01硬编码为端点。
2. 一台设备仅一个Bulk写者；帧内部不插入另一帧或未经验证的命令。
3. 所有24bit偏移/长度为大端；offset连续；只有末片为0x69。
4. 0x68头8B，0x69头11B；传输预算包含头；实际写长度不得使用租借buffer总容量。
5. 当前基线单帧≤1MiB、常规单次写入≤240KiB，并取设备/WinUSB更小限额。
6. JPEG必须完整、结构和尺寸合规；SOI/EOI不是充分合法性证明；不得截断“压到上限”。
7. 短写、超时和取消造成同步不确定后不得续发剩余JPEG，必须进入已验证的恢复流程。
8. 不任意padding凑512；ZLP/短包策略以固件联合测试冻结，不能把应用Write边界等同request边界。[W6]
9. EP0请求的bmRequestType、bRequest、wValue、wIndex、wLength逐项定义；class的0xA1与vendor的0xC1不能混用。[W7]
10. 未知能力默认关闭。不能以“未知命令目前被忽略”为由探测性发送。
11. 退出与普通待机不发送`AF 20 1F 02`；纯熄屏必须有明确固件能力。
12. 0x20只有一字节val；长时间、大参数、OTA不得截断或借用保留字段。

上述协议原始依据为S1 Part B、S2 §4；边界与语义补充见ISS-03～ISS-15。固件必须验证Windows显示驱动触发息屏/关闭显示器时的行为，不仅检查“上位机没有主动发POWERDOWN”。R1纯熄屏与系统电源处理不得造成意外设备复位；旧固件行为仍按兼容档显示限制。

## 7. HID、模式与反馈规范

读取HIDP_CAPS后确定Input/Output/Feature长度，报告长度包含Report ID。[W8] 选择vendor collection必须校验UsagePage/Usage和稳定设备身份；不得仅按VID/PID拿到第一个HID句柄。

Report ID、命令号与字段偏移必须来自冻结契约。ACK至少区分Accepted和Applied；原文未定义完整回执时不得自行发明“执行成功”。模式命令使用绝对目标；重枚举后的新PID只是过程事件，不能直接视为完成。

目标Theme的就绪判定包括接口打开、能力检查、协商和首帧传输；设备呈现确认另列。目标Screen还要确认厂商显示驱动和对应显示拓扑。失败回滚只能在实际观察到原态可用后完成。

USB的传输握手并不能证明LCD呈现。[W9] 不得把Bulk完成次数命名为displayed_fps；固件FPS/帧计数也必须先确认表示接收、解码还是呈现。16bit计数需处理回绕，设备重启与计数回绕必须有可解释策略，不能靠未经确认的推断产生“丢帧率”。

同一参数可能由HID和显示驱动控制，必须冻结优先级。副屏态不应通过频繁HID写入与系统电源/亮度策略对抗；UI以实际报告值为依据，并按固件能力说明控制可用性。

## 8. UI 与交互规范

管理UI仅采用Fluent UI Blazor；不夹杂另一套控件、随意复制CSS框架或用不同状态颜色表达同一含义。采用统一Design Tokens，字体层级、间距、圆角、状态文案和禁用态集中管理。

所有命令入口必须同时检查连接、模式、能力和忙碌状态。主窗口与托盘读取同一RuntimeSnapshot，不能各自维护CurrentMode。禁止假进度条；模式切换显示真实阶段，如停止推流、等待重新连接、检查驱动、初始化主题。

普通用户错误提示包含问题、可行动的下一步和诊断编号；原始异常、设备路径和堆栈不直接暴露。对不支持能力明确说明，而不是让用户按一个永远无效的按钮。

UI预览不得被标成“设备画面”，除非确有设备回传；本项目首版没有抓回设备实际画面的能力。来源缺失或采样过期的指标必须有视觉和文本提示。管理窗口大小不影响物理JPEG尺寸。

## 9. 配置、主题与输入安全

配置使用schemaVersion与严格值域，禁止把未知字段自动变成可执行功能。原子写入、备份回退与迁移测试是必需项。未知较新schema不得直接降级覆盖。

主题只允许受控数据与素材。导入路径归一化并限定根目录，防止`../`、绝对路径与符号链接逃逸。限制文件数、总大小、像素解码预算和解码时间；可选压缩主题包未来还要限制解压后总量。损坏图片不得阻塞状态机。

不加载用户目录下任意native DLL，不执行主题脚本，不把文件路径直接拼进shell命令。正式native依赖来源、架构、版本、校验值和许可证必须记录。

主应用普通权限运行。需要权限的采集按《03_软件技术架构》隔离或降级；不得要求关闭防护、驱动签名验证或系统安全功能。许可清单是交付核对项，不在本文件中给出超出已获取许可文本的法律结论。

## 10. 日志、隐私与指标规范

日志必须结构化，公共字段统一；高频正常路径摘要化，错误携带OperationId、SessionEpoch、脱敏DeviceKey、固件/驱动/协议版本。禁止每帧落全量JPEG、无限十六进制dump或持续打印每个像素/传感器。

日志滚动、总量与保留期限均有上限。导出默认不含主题图片、桌面捕获、完整用户名路径或内存转储；这些内容只有明确说明后才可另行选择。默认不向公司云端发送设备诊断或个人PC指标。

指标名称定义单位和口径，尤其区分：主动丢弃待发帧、USB失败、设备解码失败、实际呈现失败。不存在数据源的指标为Unknown，不用0表示“没有问题”。

### 11.3 实机证据模板

每份报告必须列：CaseId、应用commit/version、SDK、协议配置档、固件hash/version、驱动包version、硬件revision、脱敏serial、Windows build、USB控制器/Hub/线材、输入素材hash、步骤、预期、实际、日志、抓包/图片、结论、执行人与日期。

已知问题要能由另一人复现；照片证据必须能对应版本和测试步骤，不能只留一张“屏幕亮了”的图片。设备呈现计数未实现时用明确的外部观察手段，报告中注明误差和人工因素。

## 12. Git / PR 规范

分支沿用：`master`、`develop`、`feature/<WorkItemID>-<short-description>`、`release/*`、`hotfix/*`。其中WorkItemID是真实Azure DevOps ID，不是文档Txxx。长期分支必须通过PR和CI保护，不直接推送。

每个PR聚焦一个可审查结果，避免把协议更改、UI重排、驱动包替换和依赖升级混在一起。协议与模式切换PR至少一名熟悉固件契约的评审者；Interop/取消/资源所有权必须人工检查，不能仅依赖自动分析器。

PR描述应采用：

```text
关联：工作项ID、Txxx、REQ/FR/ISS
目标：本次解决的具体问题
范围：变更模块与明确不包含的内容
契约：是否改变wire格式、能力、时序、默认行为
风险：设备状态、句柄、旧固件、驱动或配置兼容
测试：已运行的Case、环境、证据链接
未运行：哪些实机Case未执行及原因（不得写成通过）
回退：代码/配置/驱动各如何恢复
文档：PRD、ADR、协议和任务同步情况
```

提交信息建议`feat/fix/test/docs/refactor/build`加模块范围和工作项引用。原生崩溃修复必须有回归用例或可复现测试步骤，不接受只延长Sleep掩盖竞态。

## 13. CI 与发布流水线规范

| 阶段 | 必须执行 | 失败处理 |
|---|---|---|
| PR验证 | 锁定SDK恢复、构建、格式/分析、非硬件单测、架构测试、协议golden | 阻止合并 |
| 集成验证 | Windows适配测试、Razor/Fluent资源、native架构与依赖检查 | 阻止集成版本发布 |
| HIL验证 | 独立样机租约、固件/驱动比对、TC矩阵、现场日志归档 | 不可用即Not Run，不能静默降为单测 |
| 安全与许可 | 依赖审查、未知二进制阻断、许可/SBOM、敏感内容扫描 | 进入人工风险评审，不自动放行 |
| 发布候选 | 自包含或明确依赖的安装包、配置迁移、签名 | 仅受保护release/hotfix流程可访问签名凭据 |
| 正式验收 | 干净机、升级回退、长稳、兼容范围确认 | 需产品/测试/技术/交付放行 |

测试Agent是Windows，不复用只具备Linux/Kubernetes工具的Agent来假装执行WPF/驱动测试。HIL Agent在运行前必须独占测试设备，禁止两个流水线同时切PID或刷写同一设备。

签名密钥、证书口令和内部发布凭据不入仓库，不输出到日志。驱动包不能从任意网盘下载后直接进入正式安装包；保留供应商来源、版本、校验和与适用硬件记录。

首版不绑定某个未经选型验证的安装器产品。安装器及运行依赖策略在T040前确定，不能以未签名ZIP代替PRD的正式安装验收。

## 14. 版本与兼容规范

应用版本、协议版本、固件版本、驱动版本、配置schema分别维护。应用升级不隐式升级设备固件。变更wire语义、字段长度或默认电源行为时，必须更新协议兼容声明与配置档，而非只改应用patch。

已知兼容组合进入release manifest；未知组合应显示未验证或不兼容，不能从VID/PID相同推断所有版本都兼容。协议里的“保留”字段禁止未经协商使用。

软件回退只保证应用与配置范围内的恢复；驱动恢复需要单独记录。由于R1不包含OTA，不得在发布说明中宣称自动恢复固件。对输入文件和主题素材的格式变更，保留备份并限制不可逆迁移。

## 15. AI辅助开发约束（可整理为仓库AGENTS.md）

AI或自动编码工具开始任务前必须阅读本任务引用的REQ/FR、协议配置档、相关ADR与既有实现，再提交范围内修改。不得根据“加个case即可”的原文就假设固件已有功能，不得发明ACK、GET_CAPS字节布局或驱动能力。

不得自行引入Dapr、数据库、远程服务或新UI框架；不得修改与任务无关的页面和颜色；不得用Task.Delay、无限重试、吞异常或catch后返回成功掩盖设备问题；不得把帧率、连接或模式状态写死。

必须明确报告：修改了什么、运行了哪些测试、哪些测试未运行、需要固件配合的内容。未经实机验证不得标记“设备联调通过”。新增协议或跨仓契约先更新并批准文档，再生成两端代码和golden vectors。

需求变更、协议边界、权限升级、签名与发布仍由项目负责人审批，不能因自动化工具“已生成实现”跳过Gate。

## 16. 合并前检查与发布底线

合并前核对需求范围、接口契约、边界单测、取消/释放、UI错误、日志隐私和文档同步。发布前再核对真实设备状态、干净机驱动、签名安装、升级回退、长稳及支持范围。

以下任一情况阻止R1：分辨率能力冲突未解决；分片/ZLP行为不确定；HID模式回程不可用；POWERDOWN导致意外复位未处理；发生短写仍续发；切换失败却报成功；标准用户无法运行基础功能；驱动只能依赖研发工具安装；关键实机测试未执行。
