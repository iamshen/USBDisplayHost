# USB Display 上位机｜需求分析

版本：v0.1 评审稿　日期：2026-10-06　暂定工程名：UsbDisplayHost

## 1. 分析口径

本项目是 Windows PC 上运行的 USB Display 主题屏上位机，目标硬件是 AD100（Darwin RTOS）与 VTDR6115 1080×2400 竖屏。本次范围仅包含设备显示与控制，不包含已有业务系统或云端微服务改造。[S2：术语、§1.1]

## 2. 产品定位与系统边界

### 2.1 要解决的问题

同一块屏幕需要两种用途：主题态显示壁纸、时钟、硬件监控仪表盘；副屏态作为 Windows 原生扩展显示器。当前设计以不同 PID 让 MI_00 分别由 WinUSB 和厂商显示驱动接管，上位机通过两态均提供的 vendor HID 发起控制与模式切换。[S2：§1.3、§2.1、§3]

本项目的关键不是先做漂亮的设置页，而是保证：设备识别正确、协议封包正确、内容能持续显示、切换后状态真实、出错能够诊断。

### 2.2 边界分工

| 范围 | 应负责的内容 | 不应混入的职责 |
|---|---|---|
| 上位机 | 发现设备、管理会话、渲染和编码、USB/HID 通信、主题配置、PC 指标采集、诊断 | 实现 LCDC/DPU 驱动、代替固件补齐未实现的命令 |
| 固件 | USB 描述符、PID/模式、HID 报告、JPEG 接收与解码、显示、设备指标、命令执行 | PC 主题排版、PC CPU/GPU 温度采集 |
| Windows / 驱动包 | WinUSB/HID 绑定、厂商显示驱动、扩展屏生命周期 | 主题业务状态、上位机配置 |
| 测试与交付 | 驱动兼容矩阵、联合协议测试、长稳测试、签名安装与诊断证据 | 通过“能编译”替代实机验收 |

### 2.3 产品角色（建议基线）

普通用户需要选择主题、看状态、调亮度和切模式；售后人员需要导出诊断并区分驱动、固件和内容问题；研发人员需要协议样例、计数器和可复现环境。首版不需要用户账号、商户、门店、云端租户或远程操作权限体系。

## 6. 必须处理的文档问题

### ISS-01｜实际分辨率与宣告能力冲突【P0 / 来源事实 + 待验证】

S1 Part A 描述 800×1280；B10 指明实际面板为 1080×2400，却又指出固件配置为 1920×1080；specific descriptor 最大宽高仍为 2047。S2 §6.6 也把这几项列为前置条件。

**处置：**建立每个硬件版本的 PanelProfile，把 EDID、specific descriptor、实际面板、JPEG 解码尺寸和 DPU 显示路径一并验收。只扩大描述符最大值并不能证明解码器、缓冲和显示层支持 2400 高度。正式版遇到冲突应阻止推流并给出原因；工程版的强制覆盖必须显式开启并记录，不可静默采用其中任一值。

### ISS-02｜现有 CDC 与目标双态被混用【P0 / 来源事实】

当前上电 CDC、AD10 单 display 与设计中的 AD11/ADA0 不是同一状态。[S1 B1、附录 C；S2 §6.6]

**处置：**G0 固化实际固件版本与启动形态。R0 最短验证允许实验室按现有 CDC 路径切出后单独绑定 WinUSB；这种配置不等于量产双模。R1 需要两套目标形态、正确接口顺序和 HID 控制闭环。

### ISS-03｜示例分片存在可复现的边界错误【P0 / 静态复核】

S2 §4.3 的代码先按 `remain <= CHUNK_MAX` 决定 `last`，据此选择 11 字节头；之后又扣除头长截断 payload，再据实际 payload 决定写入 `0x68` 或 `0x69`。这两个“最后一片”的判断不一致。

令 `C = 240 × 1024 = 245760`。当 `remain ∈ [C−10, C]`，也就是 **245750～245760 字节**时：

- 预先的 `last = true`，因此分配 11 字节头并写 3 字节 pixel_offset；
- payload 最大只有 `C−11 = 245749`，没有发完剩余数据；
- type 实际却被写为 `0x68`，该类型正确头长应为 8 字节。

结果是多出的 3 字节混入 JPEG 数据解释范围，并可能令后续协议解析错位。该结论针对附件示例，不代表已经证明固件仓库含有同样代码。

建议统一用 `payloadLimit=C−11`，先决定 payload，再由 `offset+payload==frameLength` 同时确定 type 与头长。此次已用独立 Python 算术模型遍历 1～1,048,576 的所有非空长度，共检查 2,785,390 个分片，满足正长度、限额、连续偏移与最终结束条件。**这只证明分片算术，不证明 JPEG 合法性、C# 实现、驱动传输或固件解码。**

### ISS-04｜一次主机写入不自动等于一次设备接收完成【P0 / 外部核验】

S1 B2 对“512 整数倍或短包”的表述不足以定义可靠的接收边界。WinUSB 的 `SHORT_PACKET_TERMINATE` 默认关闭；启用后，写入长度为端点最大包长整数倍时会补 ZLP。[W5]

**处置：**区分应用 Write、USB transaction、设备接收 request、0xAF 记录四种边界。候选方案为一次写入一个完整记录，并在验证固件 ZLP 行为后启用 OUT 的 short-packet termination；非整数倍自然以短包结束。禁止自行填充任意字节“凑 512”。正式 Gate 必须覆盖 512、1024、分片上限及跨记录组合；不能只靠主机函数返回推断固件接收布局。

### ISS-05｜EP0 的 class / vendor 请求类型混写【P0 / 外部核验】

S1 §2、B7 把 `0xC1` 同时写成 vendor/interface 与 class/interface。按 USB setup 位定义，IN + CLASS + INTERFACE 为 `0xA1`，IN + VENDOR + INTERFACE 为 `0xC1`。[W6]

**处置：**固件负责人核对 `display_req_match` / `display_func_setup` 和抓包，分别冻结 bmRequestType、bRequest、wValue、wIndex、wLength。已定义的 vendor 状态请求暂按原文 `0xC1.01` 验证，不能因为文字纠错就擅自把实际请求改成 `0xA1.01`。

### ISS-06｜WCID 描述过度简化【P0 / 外部核验】

S2 §2.2 写成“vendor 请求 0xEE”。MS OS 1.0 的 `0xEE` 是 OS 字符串描述符索引；扩展查询使用描述符提供的 `bMS_VendorCode`，并需要正确的 WINUSB compatible ID 与接口发现信息。[W7]

**处置：**为目标 vendor 接口实现完整 MS OS 描述符和稳定接口 GUID；在未装过开发驱动的干净系统验证。不要把 HID 接口覆盖绑定到 WinUSB，也不要将 Zadig 当成正式安装步骤。

### ISS-07｜HID 能力、ACK 与身份契约尚未闭合【P0 / 来源事实 + 待验证】

S2 §4.5 给出的 64B Input、Output ID 2、Feature ID 3 不足以完成可靠命令关联：版本、能力位定义、RequestId、ACK 阶段、错误码、超时与幂等语义都未冻结。实际 HID API 长度应以 `HIDP_CAPS` 为准，报告长度包含 Report ID，不能在“64/65 字节”之间猜测。[W8]

**处置：**HID 消息独立版本化；新增字段先评审。按设备序列号、接口用途与 UsagePage/Usage 找到 vendor collection，不能仅 `hid_open(VID,PID,NULL)` 取第一个。切换后的设备路径和 HID handle 必须重新打开。

### ISS-08｜切换失败不能只把内存状态改回原态【P0 / 静态复核】

S2 §3.5 先发切换再停推，存在显示链路与重枚举竞争；§3.7 的“回到原态”也没有完整的设备侧确认条件。

**处置：**主题切副屏前先停止接受新帧、结束或取消在途 I/O、释放 WinUSB，再经仍有效的 HID 发绝对目标模式命令。新 PID 出现仅表示枚举，不代表目标功能可用。失败后进入 Recovering/Unavailable，只有重新发现设备并验证模式后才显示“已恢复”。HID 在重枚举期间会消失，不是物理意义上始终在线。

### ISS-09｜POWERDOWN、纯熄屏和队列复位必须分开【P0 / 来源事实】

`AF 20 1F 02` 在文档所述 DISPLAY 固件中会复位，不能用于退出或普通待机。[S1 B4.2、B13；S2 §3.5] EP0 SOFT_RESET 的已知效果是重建接收请求队列，是否同时清理残留、拼帧池、待显示队列尚无充分说明。

**处置：**普通关屏只开放已确认支持的纯熄屏能力。恢复契约必须定义 parser reset 的范围；范围不明时，不承诺仅一次 EP0 请求就能恢复任意错位。

### ISS-10｜没有 Bulk IN 不等于 USB 层没有流控【P1 / 外部核验】

S2 §1.5 的表述过强。Bulk OUT 仍有 ACK/NAK 等 USB 传输层握手；缺失的是应用层的解码、队列和实际呈现反馈。[W9]

**处置：**区分 `submitted`、`usbCompleted`、`deviceDecoded`、`devicePresented`。没有设备反馈时后两项显示未知，不能把 USB 写成功次数当成屏幕实际 FPS。

### ISS-11｜静态保帧不需要伪造“每秒至少一帧”【P1 / 来源冲突】

S1 B8 建议每秒至少一帧，但同节也说明停推定格；S2 §4.3 明确静态内容不推帧。

**处置：**首版采用变更驱动，时钟/监控按数据更新；连接健康通过受支持的 HID/EP0 查询独立判断。除非后续固件明确引入 watchdog，否则不把持续 JPEG 视为保活要求。

### ISS-12｜RGB565 与 JPEG 压缩码率不能混为一谈【P1 / 静态复核】

S1 将 COLOR_FORMAT 用于 rlx 缓冲 bpp，而 JPEG 路径为解码到 NV12；S2 §5.3 的“RGB565 省带宽”不能直接推广到所传输的 JPEG。

**处置：**主题态仍可按兼容基线协商 RGB565，但 JPEG 帧大小由图像内容、尺寸、质量和采样格式等决定。以编码后字节数做预算，而不是从 COLOR_FORMAT 推导带宽收益。

### ISS-13｜Windows 热插拔需要版本和实现约束【P1 / 外部核验】

源文直接依赖 `libusb_hotplug_register_callback`，未锁定版本。libusb 1.0.30 于 2026-05-17 的 ChangeLog 已包含 Windows hotplug，不能沿用“Windows 永远不支持”的旧判断；选用时仍须检查所用构建及运行时能力。[W10]

**处置：**本项目 Windows 后端优先采用 `CM_Register_Notification` 与接口枚举：先注册，再枚举并去重，避免漏掉已插入或竞态出现的设备。[W11]

### ISS-14｜触摸自动关联与坐标上限不能直接保证【P1 / 外部核验】

S2 §4.6 认为已有唯一序列号就满足自动关联，并要求 Logical Maximum 等于宽高。Windows 外部触摸设备映射依赖显示器与 digitizer 的 Container ID 一致；单独有序列号并不构成充分证据。[W12]

**处置：**冻结 HID logical 坐标范围并做归一化，使用渲染变换的逆矩阵做命中测试；不要混用 `0..1080`、`0..1079` 等边界。双态测试必须防止主题态触摸同时被 Windows 解释成主屏操作。

### ISS-15｜命令号和未来兼容性不能靠约定猜测【P0 / 来源冲突】

S1 B13.2、S2 §3.8 定义 `0x31` 为模式切换，S1 附录 C3 却举了 `AF 20 30 01`。同时“0x30+ 永远无冲突、未知命令总安全”的断言只适用于所观察的实现，不能保证后续固件或驱动。

**处置：**以经评审的命令注册表为唯一实现来源；模式切换草案采用 `0x31`，在 G0 核验。未知能力默认关闭，禁止靠试发命令检测功能。VID/PID 的量产使用与驱动匹配须由硬件供应方确认，不能由上位机随意占号。

### ISS-16｜性能数字不足以形成商用承诺【P1 / 来源事实 + 待验证】

S1 B11 的约 26fps、S2 的 15～30fps 镜像档位是特定配置下的描述/建议，没有完整测试条件。切换保留最后一帧也依赖固件不重新初始化 LCDC；不能保证所有失败路径绝不黑屏。

**处置：**R0 从 1080×2400 / 5fps 验证起步，按质量、实际帧字节、USB 完成、设备呈现、资源占用形成测量结果。高帧率与淡化过渡保留为后续优化，不阻塞主题屏基础交付。

## 9. 分析结论

最合理的实施顺序是：**先固定固件与接口契约，再跑通 C# 最小推帧闭环，然后做主题与监控，最后联合验收 HID 双模和正式安装。**

本项目需要的是可测试的 Windows 模块化桌面程序，而不是分布式微服务。与既有技术栈的最佳结合点是 .NET、Blazor/Fluent、DI、Stateless、可观测性和 Azure DevOps；USB 字节流、句柄生命周期及固件能力应成为最受约束的边界。
