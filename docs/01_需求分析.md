# USB Display 上位机｜需求分析

版本：v0.5 WPF UI 展示层设计基线　日期：2026-10-07

## 1. 需求依据

本项目是 Windows 上的 USB 显示设备工具，主要业务是设备连接、主题内容生成、画面传输和模式控制。采用 C#/.NET 开发，技术选型依据设备通信、显示和本地交互需求确定。

| 代号 | 来源 | 使用方式 |
|---|---|---|
| S1 | [USB 副屏协议与局部刷新原理](参考资料/USB_副屏协议与局部刷新原理.md)，2026-10-05 | 协议字段、现状描述、扩展设计 |
| S2 | [上位机实现文档](参考资料/上位机实现文档.md)，2026-10-05 | 产品用途、双模设计、主机流程和固件待办 |
| D | 本次设计 | 产品范围、原生桌面实现、默认值和验收目标 |
| V | 待验证 | 附件不能确定、描述冲突或需要实际设备证据的事项 |

S1/S2 的“已实现”和“实测”是原作者陈述。本次没有固件仓库和设备，不将其写为已经验证的项目事实。项目文档的性能值均是目标或实验参数。

## 2. 产品定位

用户将同一设备用于两种场景：

1. **主题态**：显示本地图片、时钟或 PC 指标仪表盘，由上位机生成画面。
2. **副屏态**：作为 Windows 扩展显示器，由厂商显示驱动输出桌面。

两种模式的画面提供者不同。上位机应让用户知道当前模式、连接是否就绪、哪些操作可执行，以及失败后该如何处理。

| 参与方 | 责任 |
|---|---|
| 上位机 | 发现与识别设备、原生桌面交互、内容生成、编码、传输、配置、诊断 |
| 固件 | 描述符、USB 接收与解析、解码上屏、HID 命令和状态、模式重枚举 |
| Windows 与驱动 | 接口绑定、原生显示器管理、系统休眠和设备通知 |
| 固件／硬件协作方 | 提供匹配版本、协议确认、串口诊断和样机 |
| 产品／测试 | 冻结范围、记录环境、验收用户流程和真实屏幕表现 |

核心功能不依赖账号、业务服务器或数据库；软件检查更新和下载使用受控的 HTTPS 发布源，支持静态文件托管。断网不影响本地主题显示与控制。首版只控制一台选定设备；接入多台时应明确选择，不自动操作第一台。

## 4. 必须解决的来源问题

| ID | 问题与依据 | 处理结论 |
|---|---|---|
| Q-01 | 默认 CDC 与目标双 PID 不一致（S1 B1、S2 6.6） | 冻结启动模式；旧样机迁移由研发操作，不要求普通用户改驱动 |
| Q-02 | 800×1280、1920×1080、1080×2400 并存（S1 3、B10） | 以已验证硬件配置及一致的描述符为准，冲突时阻止推帧 |
| Q-03 | 描述符最大高度 2047，小于 2400（S1 4） | 核查解码、缓冲和 DPU 路径，不能仅修改一个常量 |
| Q-04 | S2 4.3 分片示例按错误阈值决定 last | 以尾片容量 T-11 判断；头长度与 type 必须由同一判断生成 |
| Q-05 | S1 将 CLASS 请求也标作 0xC1 | VENDOR IN/INTERFACE 为 0xC1，CLASS 对应 0xA1；以固件匹配逻辑和抓包冻结 |
| Q-06 | 单次主机写调用被视为设备接收边界（S1 B2） | USB 请求边界并非天然一致；验证短包、ZLP 和固件解析 |
| Q-07 | SOFT_RESET 仅描述重建请求队列（S1 B7） | 另行确认是否清除残片、拼帧块和错误状态；不假设完成全部恢复 |
| Q-08 | HID 的 64B 表与 65B 缓冲示例混用（S2 4.5） | 从报告描述符取得长度，冻结 Report ID 是否计入长度 |
| Q-09 | 能力、版本、ACK 缺少完整定义 | 固件与主机共同冻结；未知能力不得试发扩展命令 |
| Q-10 | “切换失败回到原态”没有观察证据（S2 3.7） | 超时后重新枚举与查询，显示实际状态或结果未知 |
| Q-11 | 主题切副屏时先切换后停止发送（S2 3.5） | 先停产帧并收敛在途写，再发切换命令 |
| Q-12 | “两态 HID 始终在线”容易误解（S2 1.3） | 两态提供 HID 不等于句柄跨重枚举存活，必须重新打开 |
| Q-13 | 不黑屏、触摸自动关联被写成保证（S2 3.6、4.6） | 依赖固件及驱动，以实测为准；无缝淡化不属于首版目标 |
| Q-14 | RGB565 被描述成能减少 JPEG 传输量（S2 5.3） | JPEG 字节数由图像和编码决定，不能由该命令直接推定 |
| Q-15 | 没有 Bulk IN 被等同于没有传输背压（S2 1.5） | 区分 USB 流控与缺少解码／呈现反馈；写成功不等于显示成功 |
| Q-16 | 自定义命令被称为“绝不冲突”“安全” | 未知版本不发送；命令分配与语义必须进入冻结协议 |

## 6. 首版范围与成功标准

V1 提供单设备双模控制、三个内置内容模板（图片、时钟、基础仪表盘）、本地图片选择、设备设置、托盘、诊断、安装包及软件更新。软件更新仅更新上位机应用，设备固件 OTA 仍属于后续范围，驱动使用独立安装维护流程。

基础仪表盘至少支持 CPU 使用率和内存占用；CPU/GPU 温度与风扇作为同一页面中的可用能力，未采集到时不显示假值。PC 温度采用可选采集组件验证，不要求应用整体常驻管理员权限。

成功标准是：选定设备能够持续显示正确内容；模式和开关操作有真实结果；出现错误时不会继续错误推流或虚报成功；用户可在普通 Windows 环境安装、运行和退出。

管理界面须在高 DPI、紧凑窗口和系统文字放大下保持可读与可操作，支持键盘、读屏器和高对比度。主题草稿、主机活动预览与设备呈现反馈须有清晰区别，相关可测目标见 PRD NFR-10、NFR-11 和 [UI 设计规范](06_UI设计规范.md)。

明确延后：视频播放、60fps、桌面镜像、触摸路由、OTA、动画下载、脚本主题、主题市场、多设备同时发送。它们不会因原文提到相关命令就自动进入首版。

## 8. 方案方向与待冻结决策

采用 Windows 原生桌面方案：C#、.NET 10、WPF/XAML＋WPF UI。产品依赖 Windows 驱动、PnP、托盘与 USB 原生接口，当前没有跨平台交付要求。WPF 提供桌面与绘图能力，WPF UI 统一管理界面的窗口、导航、主题和常用交互；具体模块与替换条件见 [技术架构](03_软件技术架构.md)。[WPF 官方文档](https://learn.microsoft.com/en-us/dotnet/desktop/wpf/)、[WPF UI 官方仓库](https://github.com/lepoco/wpfui)

.NET 10 按官方支持政策列为 LTS，作为新项目运行时基线；实际 SDK 和依赖补丁版本在建项时锁定，不在本文猜定版本号。[.NET 支持政策](https://dotnet.microsoft.com/en-us/platform/support/policy)

待冻结事项包括：固件协议、受支持 Windows build、WPF UI 版本及桌面交互兼容结果、编码器兼容结果、可用传感器矩阵、Velopack 工具版本与签名配置、更新发布地址和运维责任人。上述事项由 [项目管理](04_项目管理.md) 中的任务负责关闭。
