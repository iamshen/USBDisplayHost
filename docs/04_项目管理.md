# USB Display 上位机｜项目管理

设计基线：v0.5　文档更新：2026-10-14

## 1. 管理方式与交付目标

项目以仓库中的需求、任务和验收记录管理，构建与验收使用仓库内统一入口。

本计划完成正式首版 V1；V0 是内部主题链路验证阶段。计划不是已完成工作记录。当前只有文档，以下任务全部为待开始，尚未承诺人员和日历日期。

任务状态统一为：待开始、进行中、待联调、待验收、已完成、阻塞。阻塞必须记录缺少的输入、提供方和下一次确认时间；不把硬件等待算作已完成。

## 2. 角色和责任

| 角色 | 责任 | 交付物 |
|---|---|---|
| 产品负责人 | 范围、默认行为、变更和发布决定 | 需求基线、变更记录、发布结论 |
| 主机开发 | WPF、协议、Windows 通信、配置和打包 | 源码、软件测试、构建包 |
| 固件开发 | 描述符、接收与恢复、HID、模式和纯熄屏 | 固件版本、协议、设备诊断 |
| 测试负责人 | 兼容环境、功能、异常、长稳与回归 | 测试记录、缺陷、验收报告 |
| 发布责任人 | 安装、签名、依赖许可和版本归档 | 正式包、校验信息、安装说明 |

一人可承担多个角色，但实机记录必须明确执行人和版本；需要固件或驱动方确认的内容不能由主机模拟测试替代。

| 阶段 | 目标 | 准入 | 完成证据 |
|---|---|---|---|

M4 固件开发与 M1～M3 主机开发可并行；M5 的安装验证应从 G0 就开始，不在最后才发现驱动不可分发。

## 4. 工作量与排期口径

在“一名主机开发、一名固件协作、测试可按阶段投入”的假设下，初始主机开发预算如下。它不包含等待供应商、驱动认证、证书采购和重大固件重构，不能直接作为交付日期。

| 工作包 | 主机开发估算 |
|---|---|
| G0 调研与最小实验 | 3～5 人日 |
| M1 最小出图 | 4～6 人日 |
| M2 传输与生命周期稳定 | 4～7 人日 |
| M3 原生 UI 与主题产品 | 7～10 人日 |
| M4 HID 与双模集成 | 5～8 人日 |
| M5 安装与问题收敛 | 4～6 人日 |
| 合计 | 27～42 人日 |

测试另预留 8～12 人日，可穿插执行；24 小时长稳包含实际等待时间。固件人日由固件负责人在 G0 后提供。G0 未关闭前只排实验，不承诺 V1 日期。

以上为初始粗估；T-29、T-30 明确了 UI 基础、可访问性和应用一致性工作，纳入 M2／M3 重新估算后再冻结预算。27～42 人日不能作为这些细化工作已经评估完成的承诺。

软件更新 T-31～T-33 纳入 M5 单独估算，包含发布源、签名、实际跨版本升级与修复验证；发布地址和签名凭据尚未配置，不视为现成基础设施。

## 6. 关键路径与并行安排

数据面关键路径：T-02 → T-04 → T-08/T-09 → T-10 → T-11 → T-12/T-13 → T-20。

正式版额外关键路径：T-05 → T-21 → T-22 → T-23/T-24 → T-26 → T-27 → T-28。

软件更新路径：T-07 → T-31 → T-25 → T-32 → T-33 → T-27。发布源和签名试验可先行，最终升级验收使用真实安装构建，不依赖设备在线。

可并行的工作包括：固件 HID 与桌面模板；驱动安装试验与纯协议测试；指标采集与配置／日志；T-07 → T-29 的原生界面基础。T-29 不依赖样机，可先验证布局和展示逻辑。前置条件尚未具备时可以模拟接口开发，但依赖硬件的任务状态保持待联调，不能转为已完成。

## 8. 任务和缺陷记录模板

实施时可将任务拆成仓库 Markdown 文件。每项任务至少记录：

- ID、标题、需求编号、负责人、状态、依赖。
- 输入版本、具体改动范围、验收条件。
- 结果链接：提交、构建、日志、图片／录像、测试记录。
- 阻塞与下一步；完成日期及验收人。

缺陷必须记录复现步骤、预期、实际、发生概率、环境版本和证据。协议问题附请求和实际完成长度；状态问题附会话代次与时间线；画面问题附测试图及实屏照片。

严重度：S0 为错误控制设备、不可恢复损坏等；S1 为核心流程失败、崩溃、虚报状态；S2 为有绕过路径的功能问题；S3 为不影响操作的表现问题。发布前 S0/S1 必须关闭，S2 由负责人根据明确用户影响决定是否延期。

## 9. 风险登记

| 风险 | 触发信号 | 处理／责任 |
|---|---|---|
| 描述符与目标 1920×1080 图解码不一致 | 测试图失败、DPU／内存限制 | 固件核查全路径；未解决不放行 M1 |
| HID 仅存在于设计文档 | 样机无 collection 或缺控制响应 | 固件提供冻结协议与版本；M4 阻塞 |
| 默认 JPEG 与设备不兼容 | SOF／采样不匹配或解码失败 | T-06 先验证；只替换编码模块 |
| 分片停止或短包导致接收悬挂 | 最后一片不完成、计数不前进 | USB 抓包＋固件日志确认 ZLP 和 parser reset |
| 驱动分发／签名受限 | 干净机无法安装、缺许可 | G0 提前确认；正式发布阻塞 |
| 重枚举串认设备 | 两台设备身份重复 | 禁止自动接管歧义设备；修正固件身份 |
| 传感器需要权限或硬件不支持 | 读不到温度或驱动加载失败 | 显示不可用，保留 CPU／内存基础指标 |
| 源文性能不能复现 | 5fps、资源预算失败 | 固定环境测量；分析渲染／编码／发送／解码耗时 |
| 范围扩大 | 提前加入 OTA、触摸、镜像 | 新建需求与独立估算，不挤占 V1 验收 |
| 固件与应用版本错配 | 同指令出现不同结果 | 发布兼容矩阵，未知组合禁止扩展控制 |
| 更新源不可用或新版本安装失败 | 检查／下载失败、文件占用、配置迁移失败 | 保留核心离线功能；发布负责人维护源、签名产物及完整安装包修复说明 |

## 10. 评审与变更

每周检查完成证据、阻塞和下一阶段输入；每个里程碑评审仅讨论范围变化、未解决风险和是否满足放行条件。需求评审与代码评审可在仓库记录，无需购买或部署项目平台。

新增依赖、支持新型号、改变协议、放宽验收目标时记录：原因、当前证据、影响的 REQ/FR/TC、工作量、决定与责任人。

## 11. 完成与发布

任务“已完成”要求实现、适当测试和对应证据齐全。模拟通过只能关闭纯逻辑部分。硬件任务需要匹配版本的真实设备记录。

正式包归档：应用版本、源码提交、SDK／依赖锁定、固件和驱动兼容表、安装包哈希、签名结果、测试记录、已知问题与恢复说明。回退应用前检查配置 schema 兼容，不能把回退应用等同于自动回退固件。
