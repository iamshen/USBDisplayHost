# USB Display 上位机｜项目管理方案

版本：v0.1 评审稿　日期：2026-10-06

## 1. 管理目标与前提

本方案将需求、固件依赖、开发任务、测试证据和发布准入串成一条链。源文 M1～M7 的出图、稳定、主题、回传、控制、切换、触摸顺序保留，并前置 G0 协议与样机基线。[S2 §6.5、§6.6]

以下任务是建议待办，不代表当前仓库真实进度；本次没有查询实际代码仓库、Azure DevOps 项目或开发人员排期。所有初始状态应登记为“待评审/未开始”，已完成项必须补证据后再调整。

沿用你的管理习惯：**Azure DevOps 工作项只使用 Task（任务），不建立 Epic/Feature 层级，不设置 Parent 导入列。**需求层级和依赖通过文档编号、Tags、描述和 Related/Predecessor 关系表达。

## 3. 责任分工

| 角色 | 对结果负责 | 主要参与 |
|---|---|---|
| 产品负责人 | 范围、默认行为、验收阈值和发布取舍 | 需求/PRD评审、用户文案、兼容范围 |
| 技术负责人 | 架构、接口边界、重大风险与ADR | 协议评审、跨模块合并、疑难恢复 |
| Host开发 | C#应用、协议封装、渲染、UI、Windows通信 | 单测、工具、联调证据 |

| 测试负责人 | 独立验收与缺陷复现 | Windows/驱动矩阵、长稳、故障注入 |

同一人可承担多个角色，但一项任务只指定一个最终负责人。协议变更、驱动包变更、模式切换与恢复逻辑至少需 Host 和固件双方评审。人员姓名与可用人力尚未给出，本文不虚构分配。

## 4. 工作量与排期口径

采用任务粒度估算，而非直接承诺若干周完成。建议 XS≤1人日，S约1～2人日，M约3～5人日，L约6～10人日；这只是首次拆分尺度，不是对当前团队的工期预测。L任务正式启动前应再拆分，未知硬件问题先做Spike。

日历计划必须结合实际人员、样机数量、固件可修改性、驱动授权与签名条件制定。多人并行不等于把所有人日相加后简单除人数；固件Gate、硬件回归和驱动审批可能位于关键路径。

## 8. Azure DevOps 工作项模板

所有项使用 `Work Item Type = Task`。推荐最小字段为 Title、Description、Tags；Assigned To、Iteration Path、Area Path 根据实际项目填写，不猜测姓名或路径。无需Parent列。

```text
Title: [USBHost] T006 建立0xAF边界golden vectors并修正分片算法
Work Item Type: Task
Tags: USBDisplayHost;G0;Protocol;P0;REQ-03

Description:
目标：消除0x68/0x69头长不一致并冻结分片不变式。
依据：S2 §4.3；ISS-03；REQ-03 / FR-03。
范围：纯协议封包、golden vectors、反向重组。
不包含：WinUSB取消、设备JPEG解码与UI。
依赖：T001。
验收：C−12、C−11、C−10、C、C+1、1MiB、超限等用例通过。
证据：测试报告、用例数据、PR、实际SDK版本。
风险：此任务不证明ZLP与固件request边界正确，后续依赖T015。
```

导入后建立前后置链接，不能只在标题里写依赖。Task大小是计划辅助，不设为“已完成工作”；Blocked 使用实际过程允许的状态或标签，并注明阻塞原因、责任人和解除条件。

## 9. DoR / DoD

### 可开始（DoR）

需求编号与范围明确；源文/协议引用可追溯；前置条件存在；错误路径和测试方法明确；涉及新增固件行为的命令号、字段和能力位已经评审。没有设备时可做的纯测试与必须等设备的验收分开登记。

### 完成（DoD）

代码与测试经PR合并；自动化检查通过；错误/取消/资源释放路径验证；相关需求和协议文档已更新；属于实机任务的测试环境、固件/驱动版本和证据已留档；不存在用Fake结果替代实机通过的情况。

“程序能运行”“演示出一张图”“单次切换成功”均不等于完成M2/M6。纯软件任务可在无样机时完成，但不能替固件Gate或整机验收放行。

| 无可用HID回程或双PID实现 | P0/R1 | 只能手动切、只能改驱动绑定 | R0内部版与R1分离，不虚构切换；固件 |
| 软复位没有清理parser | P0 | reset后仍花屏，下一帧被当残留 | T003契约和T018故障注入；固件+Host |
| 驱动无法正式分发/签名/自动匹配 | P0/R1 | 干净机失败、只在开发机成功 | T005提前取得依据，T041单独验收；交付 |
| 传感器权限或硬件覆盖不足 | P1 | 无温度或依赖提升权限 | 支持表、降级与可选隔离；Host/产品 |
| 切换UI与实际模式不一致 | P0 | 新PID出现就报成功、无驱动仍显示副屏 | 目标operational验证；T037/T038 |
| 计数器回绕导致假异常 | P1 | 长稳后FPS或丢帧突跳 | 冻结计数语义、回绕与boot区分；T031 |
| Native/WebView资源泄漏 | P1 | 托管堆稳定但进程树持续增长 | T016、T042观测native和子进程 |
| 触摸、OTA范围膨胀 | P1 | 新增入口后默认“命令已经可用” | 变更评审、独立R2；产品负责人 |

## 11. 评审与协作节奏

每日同步仅讨论阻塞、接口变更、实机结果和下一个可验收结果。每周评审需求/风险/完成证据；协议变更不等到周会，发起专项评审。Host与固件联调使用同一版本组合清单，禁止一方升级未告知另一方。

每次演示同时展示正常路径和至少一条失败路径，例如无驱动、半帧拔出、未知能力或切换超时。用“已完成、待验证、被阻塞、范围外”四种口径汇报，不把待验证项放进完成数量。

## 12. 变更管理

涉及字段、命令、分辨率、PID、默认模式或功能范围的变更，需记录：理由、受影响REQ/FR、协议/驱动兼容性、工作量、测试增量、回退方式。批准后同步PRD、ADR、协议契约、Task与测试；不只修改代码常量。

协议修改必须保留版本和兼容档。旧版本不支持的命令不得由Host自动探测性下发。重大风险未关闭时可缩小R0范围，但不能把降低范围后的演示版按原R1标准宣传。

## 13. 发布与回退清单

正式发布档案应包括：应用包与校验值、签名信息、固件/驱动版本组合、兼容硬件与Windows范围、NuGet/native依赖和许可、测试证据索引、已知问题、升级/回退/卸载步骤、诊断导出说明。

应用回退、驱动恢复和固件降级是三项不同操作。R1没有OTA能力，因此不承诺通过上位机自动回退固件。驱动恢复不得误删除其他设备共用包；升级前备份配置并记录schema。
