# 整帧传输执行者实施记录

关联：REQ-03／FR-03、REQ-09／FR-09、T-11／T-12、任务 5.2／5.3、jpeg-frame-transport。日期：2026-10-08。

## 实施范围

`FrameTransferExecutor` 属于 Core，不引用 WPF、原生句柄或 WinUSB 类型。每个执行者冻结设备键、会话代次、已验证能力、固件 JPEG 清单和传输上限。新通道初始为 `RecoveryRequired`，不能仅凭打开接口开始发送；显式恢复必须取得同设备、代次、操作和固件的 parser 清理收据并确认恢复 I/O 收敛。

发送前调用完整 JPEG 校验，核对返回的尺寸／格式，建立 AF 分片计划，再核对帧边界的操作、内容修订及推流状态。一个调用执行中时立即拒绝并发发送／恢复／提前 Drain，没有内部待处理队列。单次分配一个不超过 245760 字节的传输缓冲；每片等待前一片结果后才重用缓冲。要求实际请求长度等于分片长度，实际完成长度相同、无原生错误、未取消且完成状态已知；不补零、不重发分片、不追加空尾片。

完整尾片成功后返回 `FrameTransferReceipt`，包含原帧上下文、帧号、JPEG 长度、片数、包字节及完成时间戳。统计只累计确认完整写入的包字节和完整 USB 帧，没有设备呈现反馈计数，不改 ActiveProfile 或恢复配置。帧内仅核对设备身份／代次；普通新内容不截断已经开始的帧。帧边界控制命令与事务首帧仍须由同一物理会话所有者授予；直接调用底层接口不能保证命令互斥，后续组合层不得暴露这种入口。

## 故障与恢复

`ValidateCandidateAsync` 提供排队前的独立准备入口，使用同一完整校验与分片限制。一候选校验与一在途发送可以并行等待校验器，WPF 校验器仍串行解码；额外候选立即拒绝，不建立无界校验队列。准备只读取冻结能力与会话守卫，不改状态／计数，不执行 USB、收敛或 parser 恢复；普通准备异常返回带编号的明确失败。实际发送再次执行同一校验，前后均核对当前帧归属，第一片前还保留最终守卫。

- 短写、原生错误／超时、取消或失去会话立即停止剩余分片，失败游标不续传。开始 I/O 前取消返回 Cancelled；开始后取消返回失败并标记通道需要清理，不暗示设备没有收到字节。
- 原生完成未知或 Write 抛出普通异常时，调用 `CancelAndDrainAsync`，不使用已取消用户令牌中断收敛。仅 Success 释放缓冲；其他结果转为 `IoUnconfirmed`／Unknown，保留缓冲与传输所有者并禁止下一帧。所属会话必须保留执行者，不能把其未知结果当作安全释放证据。
- 非取消写失败允许至多一次自动 parser 恢复；必须有恢复适配器且仍满足推流条件。失败帧不会重发，即使清理成功也返回原发送失败。连续失败在完整新帧成功或显式用户恢复之前不会重新开放自动周期。取消／失去会话不自动执行恢复。
- `IFrameParserRecovery` 要求冻结契约认可的清理、保持电源意图及实际清理收据。没有默认实现，也没有把 ResetPipe 当成 parser 清理。恢复异常、取消和成功均须调用独立 Drain；无法确认恢复 I/O 收敛时保留恢复所有者，返回 Unknown。
- 普通异常在发送／收敛／恢复边界记录错误编号并返回结果，不自动重试或伪造成功。进程级致命异常的限制仍按工程基线处理。
