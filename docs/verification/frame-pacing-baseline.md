# 发送节奏实施记录

关联：REQ-03／FR-03、REQ-09／FR-09、T-12、任务 5.4、TC-16／TC-27。日期：2026-10-08。

## 生产逻辑

Core `FrameRateController` 采用已验证 DeviceSettings 的用户上限 1～5fps。没有 FramePacingPolicy 时固定按该上限调度，不使用演示延迟值。自适应策略必须显式登记延迟阈值、连续慢帧数、健康样本最大间隔及测量证据引用；不存在当前已经冻结的真实测量策略。

只使用完整发送收据：从发送执行者调用前到完整 USB 收据时间，包含 JPEG 校验与传输执行，排除渲染和调度排队；这是主机发送用例耗时，不是纯 USB 线缆延迟或生产 P95。连续慢帧达到登记次数降低 1fps，最低 1fps；健康成功样本稳定累计 30 秒才提高 1fps，每一级重新计算 30 秒，始终不超过用户上限。用户降低上限立即约束当前值，提高上限时自适应模式仍逐级恢复。

过长无帧间隔重置连续慢帧及稳定窗口，静态主题空闲不能换算为稳定发送。样本间隔必须小于 30 秒恢复窗口；仍须通过实际动态内容负载测量选择它。只接受当前计时的一次成功收据，重复、负耗时或不匹配样本拒绝。失败／取消不作为拥塞成功样本；协议恢复未确认或结果未知则停流，不通过降速掩盖。已确认恢复后清除错误及计时窗口，保留原降速结果，不立即跳到最高帧率。

## 调度组合

FrameBoundaryScheduler 与发送执行者／控制器必须共享同一 TimeProvider。每次出槽前核对节奏等待，包括受保护首帧；控制仍优先，不受帧率等待限制。等待期间不取走待发帧，保留普通帧替换及首帧保护；新工作／控制／退出可唤醒等待，等待完成再核对队列和所选对象，防止旧引用出槽。

任一时刻最多一个计时等待和一个唤醒等待，取消后等待两者结束，没有遗留 WaitAsync 读取后续信号。计时／等待普通异常返回错误编号并停后续帧，不把成功 USB 收据改为失败。只有允许继续推流的已确认帧边界控制才重置恢复计时；实际操作仍需原生和状态守卫。
